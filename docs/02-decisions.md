> One entry per significant decision. Newest on top. Format: date · decision · why · rejected alternatives.

## D-027 — 2026-08-29 · Bon printing uses French UI labels + business logo; transliteration narrowed to user data only
- **Decision:** `buildBonTicketLines` no longer wraps every string in `transliterate()`. UI labels (N°, Date, Client, TOTAL, Signé) are French — call site forces `lng: 'fr'` via `bonTicketLabels((k) => i18n.t(k, { lng: 'fr' }))`. Only user data (businessName, partyName, line.label) is transliterated when it contains Arabic. New `kind: 'raw'` TicketLine variant carries pre-encoded ESC/POS bytes (logo bitmap). Backend gains `POST/GET/DELETE /admin/logo` endpoints (follows products image pattern). Mobile settings gets logo upload card via `expo-image-picker`. `logo-cache.ts` fetches logo, decodes via Skia, thresholds to 1-bit, converts to ESC/POS raster, caches in memory.
- **Why:** User wants professional French bons, not transliterated Arabic labels. Transliterating "Bon de livraison" to itself was a no-op; transliterating Arabic UI labels produced unreadable phonetics for French speakers. French labels are the natural choice for Moroccan SMB receipts. Logo adds brand identity to printed bons.
- **Rejected:** transliterate all strings including labels (D-026 approach — labels were never Arabic on the printed ticket anyway); render logo as separate raster print before text ticket (adds complexity, two print jobs); store logo in base64 in the database (wastes DB space, `LocalStorageService` already handles file storage).

## D-026 — 2026-08-29 · Arabic print content is transliterated to French-phonetic Latin; raster path dropped for bons
- **Decision:** New `mobile/src/services/printer/transliterate.ts` converts Arabic strings to French-phonetic Latin before printing (ب→b, ش→ch, و→ou, al- prefix, shadda doubling). `bonNeedsRaster()` always returns `false` — all bons print via ESC/POS text regardless of language. Product names, client names, business names are transliterated at print time (display unchanged).
- **Why:** Mac-side hardware testing confirmed WD8007 has zero Arabic text support (all 48 codepages tested, CP1256 visual/logical, UTF-8 — none render readable Arabic). Codepage 40 showed isolated Arabic glyphs but no shaping. Raster path renders perfect Arabic via CoreText but BLE serial is too slow/unreliable for the 10KB+ image payloads (hangs, buffer overflows). Transliteration gives instant ~200-byte text prints with no firmware dependency.
- **Rejected:** raster-only for Arabic (BLE throughput bottleneck, 10s+ transfer, buffer overflows on cheap firmware); keep trying text-mode Arabic encodings (48 codepages exhausted, none work); per-line hybrid raster+text (complexity for zero gain when transliteration covers it); OCR-based translation (overkill — product names are proper nouns, phonetic transliteration is sufficient for receipts).

## D-025 — 2026-08-28 · Bon print is hybrid: Arabic content → raster bitmap (system-font shaping), fully-Latin content → ESC/POS text ticket
- **Decision:** `bonNeedsRaster()` (`mobile/src/services/printer/bon-ticket.ts`) routes each bon at print time: raster via restored `PrintableBon` + `printReceipt` when the UI language is `ar` or businessName/partyName/any line label contains Arabic (`hasArabic()` regex over the Arabic Unicode blocks); ESC/POS text ticket (D-024 path) otherwise. Text-mode Arabic machinery (modes, `ESC t`, scan) stays in Printer Diagnostics for future printers; the Arabic test now prints all three modes on one labeled paper.
- **Why:** Device evidence from the WD8007 code-table scan: the firmware carries Arabic glyph tables (n=10/20/22 print connected Arabic) but renders our cp1256/UTF-8 byte text as glyph soup in every mode — its Arabic path expects a byte layout we cannot produce blindly. Raster with the threshold-200 fix prints system-font-shaped Arabic perfectly, so correctness wins on Arabic bons; Latin bons keep the ~100× smaller, instant text path.
- **Rejected:** always raster (Latin bons pay bitmap cost for nothing); keep pushing text-mode Arabic byte permutations (unbounded trial-and-error against undocumented firmware); per-line hybrid inside one ticket (mixing raster strips and text lines breaks vertical alignment and doubles the failure surface).

## D-024 — 2026-08-28 · Thermal bon print switches from raster bitmap to ESC/POS text mode; Arabic encoding is a calibrated preset (cp1256 visual / cp1256 logical / UTF-8), not a hardcoded guess
- **Decision:** Bon printing on mobile no longer captures the React view into a bitmap — `buildBonTicketLines` + `buildTicket` (`mobile/src/services/printer/{bon-ticket,text,arabic}.ts`) emit ESC/POS text commands (48 columns, font A). Arabic is prepared in-app (visual reordering of RTL runs, digits kept LTR) and encoded to Windows-1256; three firmware modes — `plain` (cp1256 + visual order), `logical` (cp1256, printer shapes), `utf8` — are selectable in Printer Diagnostics together with an `ESC t` code table (auto or 0–255) and a "scan tables" print (48 labeled samples). Raster path stays for POS receipts/POs, with the bitmap threshold raised 128 → 200 (downscaled anti-aliased text was erased; only solid dashed rules survived — the "prints only dashes" bug).
- **Why:** The WD8007's raster buffer/decoder produced blank tickets (dashes only) even in `ESC *` mode; text commands are the native path these firmwares cannot get wrong. cp1256 is the Arabic table these Chinese firmwares ship (base forms only — no presentation forms in cp1256, so in-app shaping to U+FExx is impossible in that byte space; letters may print disconnected in `plain` mode). Firmware behaviour is unverifiable remotely, so the debug screen calibrates mode + code table once per printer instead of shipping a guess.
- **Rejected:** keep rasterising with a fixed threshold alone (image path already proved flaky on this printer and costs 100× the bytes over BLE); ship presentation-form shaping + CP864 bytes (cp864 table unreproducible from memory and rarely present on JieLi firmware); hybrid bitmap-Arabic lines (keeps the broken raster path on the critical route).

## D-022 — 2026-08-18 · Expense categories become a per-tenant table (`ExpenseCategoryDef`); `Expense.category` demoted from enum to free string; validation lives in the service layer, not a DB FK
- **Decision:** Expense categories are now rows in a new `expense_category_defs` table (per-business: `key`, `label`, `taxRate`, `sortOrder`, `archived`), managed via `GET/POST/PATCH/DELETE /expense-categories`. The Prisma `ExpenseCategory` enum is dropped; `Expense.category` becomes `String @default("other")`. Every new business is seeded with 9 canonical defaults (`DEFAULT_EXPENSE_CATEGORIES`) in the same transaction as the business row; the same list backfills existing businesses in the migration. Write-side validation (`ExpensesService.assertCategoryUsable`) rejects unknown or archived keys per tenant on create/update; no DB-level FK from `Expense.category` → `ExpenseCategoryDef.key`. Deletion of a still-referenced category soft-archives (`archived=true`) instead of failing; unreferenced categories hard-delete. TVA auto-calc on both clients now reads the selected category's `taxRate` instead of a hard-coded 20 %.
- **Why:** SMB accountants want their own chart of expense accounts — hard-coded enums forced them to shoehorn everything into 9 fixed buckets. A table also lets per-category default VAT rates drive the form's TVA auto-fill, which is the second half of the same UX ask. String column + service-layer guard (rather than an FK) keeps historical rows valid after a category is renamed or removed — the accountant's export still resolves the historical key even if the config has moved on. Seeding defaults per business (not globally) keeps categories genuinely tenant-owned: renaming "Loyer" → "Rent" for an English tenant doesn't leak across businesses.
- **Rejected:** keeping the enum + adding an `ExpenseCategoryConfig` overrides table (two sources of truth, still can't add custom categories without another writable table); FK from `Expense.category` → `ExpenseCategoryDef.key` (blocks deletion of legacy categories a tenant no longer uses; would need a nullable variant + separate resolution logic — more code for a case the service-layer guard already handles); global seed table with per-tenant overrides (users asked for per-tenant categories, not a shared taxonomy — this is a Moroccan SMB, not a marketplace).

## D-021 — 2026-08-15 · Tenant middleware: `findUnique` passes through + post-filters on `businessId` (no rewrite to `findFirst`)
- **Decision:** `makeTenantMiddleware` no longer rewrites `findUnique`/`findUniqueOrThrow` on tenant models. It runs the query as-is, then drops the result if `record.businessId !== ctx.getBusinessId()` (returns `null`, or throws for `orThrow`). All other actions still auto-scope via `where.businessId`/`data.businessId` injection.
- **Why:** the previous rewrite turned any `findUnique({ where: { productId_warehouseId: {...} } })` into `findFirst` + an extra top-level `businessId` — but compound-key aliases like `productId_warehouseId` only exist in `WhereUniqueInput`; on `findFirst` Prisma rejects them with `Unknown argument productId_warehouseId`. Every `POST /v1/movements` hit this via `StockLedgerService.applyDelta` (500). `BusinessModule.findUnique({ businessId_moduleId })` in `ModuleGuard` had the same latent bug, dormant only because no route wore `@RequiresModule` yet.
- **Rejected:** flattening compound keys inside the middleware (fragile, one branch per compound alias); switching every caller to `findFirst` (loses the unique-index hint, spreads tenant knowledge into every repo); dropping tenant auto-scope entirely (regresses defense-in-depth).

## D-020 — 2026-08-15 · Multi-stock + TVA become platform-managed settings (super admin only), read-only for tenant admins
- **Decision:** `Business.multiWarehouse` and `Business.enabledVatRates` are now toggled exclusively via `PATCH /v1/admin/platform/businesses/:id/settings` (`{ multiWarehouse?, tvaEnabled? }`, PlatformAdminGuard). Tenant `PATCH /v1/admin/vat-rates` + `PATCH /v1/admin/multi-warehouse` removed (GETs kept for display). TVA off ⇒ `enabledVatRates=[0]` (existing convention, VAT defaults to 0 everywhere); TVA on ⇒ `[0,7,10,14,20]`. - **Why:** these are plan/module-level switches, not tenant preferences — tenant admins toggling them caused inconsistent data (orphan warehouses, VAT surprises); user wants control centralized in the super-admin web console with effect on both clients.
- **Rejected:** modeling them as `business_modules` rows (they gate data shape, not endpoints — ModuleGuard semantics don't fit); keeping tenant setters alongside PA setters (two write paths, conflicting invariants); auto-merging stock when disabling multi-stock with several warehouses (silent data movement too risky — explicit 409 instead).

## D-019 — 2026-08-14 · Monthly expense export = single PDF (summary + receipt pages); webp receipts converted to png via `sharp`
- **Decision:** `GET /v1/expenses/report?month=YYYY-MM` returns one pdfkit A4 PDF: expense table + per-category subtotals + grand total, then one page per receipt image. New dep `sharp` converts webp → png at export time (`ExpensesService.loadReceipt`) because pdfkit embeds only JPEG/PNG; missing/unreadable files degrade to a placeholder instead of failing the export. `seed.ts` now seeds the 7 default `business_modules` rows — ModuleGuard requires a row, so a freshly seeded DB 403'd every module-gated route.
- **Why:** single file is easiest to share/print for an SMB's accountant; pdfkit pattern already existed (delivery-notes); sharp is the standard native image lib and only runs on export, not upload.
- **Rejected:** ZIP of PDF + originals (multi-file handling for marginal quality gain); Excel/CSV + images (new lib, no image embedding, accounting-import need not expressed); storing receipts pre-converted to png at upload (would touch the existing scan path and inflate storage for a rare export case).

## D-018 — 2026-08-12 · Weighted-average cost (`StockLevel.avgCost`) updated only on positive deltas that carry a `unitCost`
- **Decision:** `StockLedgerService.applyDelta` recomputes `avgCost = (existingQty * existingAvg + delta * unitCost) / (existingQty + delta)` only when `delta > 0` AND the caller passed `unitCost` (i.e. PO receive). Negative deltas (sales, outbound transfers, adjustments) never touch `avgCost`. Ledger callers that don't know a unit cost (inventory count, out-movement, DN sign) omit `unitCost` and leave the field unchanged.
- **Why:** Cost of goods only enters the ledger on procurement — that's the classical WAC input. Recomputing on outflows either (a) discards information (using sale price would corrupt cost basis) or (b) needs a separate FIFO/LIFO layer, which Phase S1 doesn't yet have. Negative-delta WAC untouched matches how ERPs treat weighted average: outflows consume inventory but don't re-price it.
- **Rejected:** FIFO/LIFO lots (deferred to Phase S3 — needs a new `Lot` table; scoped out of S1 per user's brainstorming answer); recompute avgCost on every write using latest transaction (loses the running-average semantics); ignore `avgCost` entirely (blocks valuation reports planned for S2).

## D-017 — 2026-08-12 · `StockLedger` is the sole writer of `StockLevel`/`Movement`; stock floor enforced via conditional `updateMany`, not read-then-write
- **Decision:** New `src/modules/stock-ledger/` module owns every stock mutation from Phase S1 onward. `StockLedgerService.post()` decrements stock with `stockLevel.updateMany({where:{qty:{gte:needed}}, data:{qty:{decrement:needed}}})` and throws `ConflictError('insufficient_stock')` when `result.count === 0`, instead of `findUnique` → compare → `update`. Positive deltas `upsert` with a weighted-average-cost recompute. `post()` accepts an optional `Prisma.TransactionClient` so callers (POS checkout, PO receiving, transfers, etc.) can fold it into their own outer transaction rather than opening a nested one.
- **Why:** The conditional `updateMany` makes the stock-floor check atomic under Postgres's read-committed isolation — two concurrent `out` movements racing on the same `(productId, warehouseId)` can't both pass a `qty >= needed` check that was read before either write landed, because the guard is *in* the UPDATE's WHERE clause, not a separate SELECT. A `findUnique`-then-compare-then-`update` sequence has a TOCTOU race window between the two roundtrips. Centralizing all writes in one service (vs. each of POS/PO/inventory/movements/products repos writing `StockLevel` inline, as they do today) means the floor guard and WAC math exist in exactly one place.
- **Rejected:** row-level `SELECT ... FOR UPDATE` locking (works but requires `$queryRaw`, harder to keep inside Prisma's typed API, and Postgres advisory/row locks add contention under load that the conditional-UPDATE approach avoids); optimistic concurrency via a version column (extra schema column + retry-loop complexity for a case the WHERE-clause approach solves directly); leaving each module's repository to keep writing `StockLevel` directly (the status quo — is exactly the race and drift Task 2 exists to close, per the S1 plan).

## D-014 — 2026-08-09 · Guard execution order: JWT → Subscription → Module → Limit → Caps
- **Decision:** Five global guards registered via `APP_GUARD` in strict order. Super admin (`type: 'platform-admin'` in JWT) bypasses all except JwtAuthGuard.
- **Why:** Each guard depends on the previous: Subscription needs `req.user` from JWT, Module needs businessId, Limit needs businessId, Caps needs roleCaps. Super admin bypass at each layer avoids DB lookups for PA requests.

## D-011 — 2026-08-09 · Unified login: single endpoint, check PlatformAdmin first then User
- **Decision:** Single `POST /auth/login` endpoint. Backend checks PlatformAdmin table by email first; if found + password matches, issue JWT with `type: 'platform-admin'`. Otherwise check User table (existing flow). PlatformAdmin stays as separate table from User.

## D-009 — 2026-08-03 · One git repository for all four apps *(superseded by D-010 the same day)*
- **Decision:** Single repo at the workspace root covering `backend/`, `web/`, `mobile/`, `ocr-service/` and `docs/`. Supersedes the per-app repo layout. **Not** a monorepo in the tooling sense — no npm workspace, no turbo; each app keeps its own `package.json`, install and deploy (D-001 stands).
- **Why:** Only `backend/` was actually versioned — `web/` and `mobile/` had git dirs with **zero commits**, `ocr-service/` and `docs/` had none, and no repo had a remote: one bad `rm` would have erased the project. Beyond that, `backend/docker-compose.prod.yml` builds `ocr` from `../ocr-service`, which only resolves inside one tree; and schema changes routinely touch backend + web + mobile together, which split repos turn into three PRs with a version-skew window.
- **Migration:** backend history rewritten into the `backend/` subdirectory (`git filter-branch --index-filter` on a bare clone — `git-filter-repo` is unavailable under PEP 668), fetched into a fresh root repo, index restored with a mixed `git reset` so the uncommitted multi-tenancy WIP was never touched. Verified: uncommitted diff hash identical before/after (`00ce901c…`), 40 modified + 58 untracked files unchanged.
- **Rejected:** separate repos per app (breaks the compose relative build context, splits atomic changes), git submodules (all the coordination cost of split repos plus detached-HEAD footguns), keeping the workspace root unversioned (docs and the mandatory progress log had no history at all).
- **Cost accepted:** CI must path-filter (`paths: backend/**`) or every push builds all four apps.

## D-008 — 2026-08-03 · Prod compose lives in `backend/`, secrets only in `.env.prod`
- **Decision:** `docker-compose.prod.yml` + `.env.prod.example` + `Makefile` moved from the workspace root into `backend/` (build context `.`). `DATABASE_URL` and every other secret come from `.env.prod` via `env_file` — never inline in the compose file. Prod publishes **zero** host ports (postgres and ocr internal-only, backend reachable only on the external `nginx-proxy` network); dev keeps `3002`/`5433`.
- **Why:** `backend/` *is* the git repo — the workspace root is not versioned, so a root-level compose file was untracked and could not ship with the code. Inline `DATABASE_URL` in compose puts a production password in git; `env_file` keeps it in the gitignored `.env.prod`. Publishing prod ports would expose Postgres and the receipt OCR service directly to the host/internet, bypassing nginx and TLS.
- **Rejected:** compose at workspace root (outside the repo, untracked), `environment:` block with `${DATABASE_URL}` interpolation (works, but duplicates the variable in two places and still needs `--env-file`), separate prod override file layered on the dev compose (dev publishes ports — an override cannot *remove* a published port, only add).

## D-007 — 2026-08-03 · Receipts served through an authenticated route, not static middleware
- **Decision:** `GET /v1/expenses/:id/receipt` behind the normal auth guard + `expenses.view`. Files live at `backend/uploads/<businessId>/<random>.<ext>`, path resolution rejects anything escaping the root.
- **Why:** A Nest static mount would make every tenant's receipts readable to anyone holding a URL. Receipts carry supplier names and amounts. Tenant-scoped paths + a tenant-filtered `findById` make cross-tenant reads impossible by construction.
- **Rejected:** static file middleware (URL = access), Postgres bytea (DB bloat), S3/MinIO (extra service now; `LocalStorageService` is the only file-path-aware class, so swapping later is contained).

## D-006 — 2026-08-03 · OCR field extraction uses bounding boxes, in Python
- **Decision:** `ocr-service/app/extract.py` matches an amount to its label by horizontal band, with a bottom-third largest-amount fallback and per-field confidence. Pure function, no I/O.
- **Why:** `image → raw text → regex` is the standard approach and it fails: OCR noise turns `RM28.20` into `IRMZ8. 20`, and decorative text defeats line-based regex. RapidOCR returns a box per fragment; flattening to a string throws away exactly the geometry that makes label→amount matching reliable. Geometry does not survive the service boundary, so extraction cannot live in NestJS.
- **Rejected:** regex over concatenated text (fragile), LayoutLM/Donut (GPU + training data for a 4-field problem).

## D-005 — 2026-08-03 · RapidOCR (ONNXRuntime), not PaddleOCR proper
- **Decision:** `rapidocr-onnxruntime`, models baked into the image at build time.
- **Why:** Same PaddleOCR-trained models, ~80 MB of deps vs ~500 MB, CPU-optimized inference (0.2–1 s/page), and no long-running memory leak. PaddleOCR's only real edge is PP-StructureV3 table parsing, which v1 does not need — no line-item extraction. Baking models avoids a first-request download failing on a fresh or offline host.
- **Rejected:** PaddleOCR (heavy), Surya (~50× slower on CPU), EasyOCR (weaker on dense receipt fonts), OCR.space free API (ships customer receipts to a third party).

## D-004 — 2026-08-03 · Dépenses OCR runs in a Python service, not a Node library
- **Decision:** Fourth app `ocr-service/` (Python 3.12 + FastAPI + RapidOCR), compose-network only, **no published host port**. NestJS talks to it behind an `OcrProvider` port.
- **Why:** Tesseract.js scores ~45% on degraded input vs ~73% for PaddleOCR-family models, and is markedly worse on the small dense fonts typical of thermal receipts. A scan that fills in the *wrong* montant is worse than no scan, because the user may not catch it. The port keeps Python out of the application layer — unit and e2e suites run with a stub.
- **Rejected:** Tesseract.js in-process (accuracy), Claude vision API (per-scan cost + sends receipts off-box), Google Cloud Vision (extra billing account, still raw text only).

## D-002 — 2026-08-02 · Product name: **Tijaru**
- **Decision:** Rename product "Stock" → **Tijaru** (Arabic *tijara* = commerce). Register tijaru.com + tijarou.com + tijaru.ma (+ tijaru.io).
- **Why:** "Stock" = generic, names one module only; app is a full suite (stock, POS, clients, factures, dépenses). *Tijara* root covers whole commerce. tijaru.com bare .com available; zero index/trademark collisions; pronounceable MA + EU. FR "u"=ü drift hedged with tijarou.com redirect.
- **Rejected:** Mizano (too stock-narrow), Caisso (POS-narrow), Tajiro (collision: Tajir YC app + TAJIRO on Play Store), Tijario (.com sniped mid-evaluation), Souko (Soko POS collision), Cashio (hacked Solana protocol), Caissa (fintech taken), Kasbah (India software co), attijaro (Attijariwafa Bank trademark risk).
